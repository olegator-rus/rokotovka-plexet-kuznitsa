# ml — эмбеддер BGE-M3 и реранкер bge-reranker-v2-m3

Нативный Python-сервис для Mac (Apple Silicon, MPS) с тем же HTTP API, что у контейнера
Text Embeddings Inference на стенде. Один процесс, один порт `127.0.0.1:8089`, оба метода.
В Docker не идёт: две модели XLM-R large не помещаются в общую Docker VM, а x86-образы TEI на M4
работают под эмуляцией.

## Запуск

```
ml/run.sh            # в текущем терминале
ml/run.sh start      # в фоне: PID в ml/.pid, журнал в ml/.run.log, ждёт /health
ml/run.sh status
ml/run.sh stop       # kill по PID из ml/.pid; по порту не гасить
```

`run.sh` сам создаёт `ml/.venv` (Python 3.13: `$PYTHON`, иначе `python3.13` из PATH, иначе
`/opt/homebrew/bin/python3.13`), ставит `requirements.txt` (повторно — только если файл изменился),
докачивает модели закреплённых ревизий в `~/.cache/huggingface/hub` и сверяет sha256 весов. Сервис
стартует с `HF_HUB_OFFLINE=1` и в сеть не ходит. Если huggingface.co недоступен, можно указать зеркало
через `HF_ENDPOINT`; sha256 весов всё равно сверяется с закреплённым.

Переменные (все необязательные):

| Переменная | По умолчанию | Что |
| --- | --- | --- |
| `ML_HOST`, `ML_PORT` | `127.0.0.1`, `8089` | адрес |
| `ML_DEVICE` | `auto` | `auto` = `mps`, если есть, иначе `cpu` |
| `ML_DTYPE` | `auto` | `auto` = `fp16` на MPS, `fp32` на CPU |
| `ML_MAX_BATCH` | `64` | максимум текстов в одном запросе |
| `ML_MAX_LENGTH` | `512` | токенов на текст (пару query+text для реранкера), длиннее — обрезается |
| `ML_MICRO_BATCH` | `32` | сколько последовательностей идёт в модель за один проход |
| `ML_RERANK_BATCH` | `32` | сколько пар реранка из одновременных запросов склеивается в одну пачку |
| `ML_BATCH_WAIT_MS` | `0` | сколько ждать соседей перед пачкой; 0 — пачку собирает сама очередь |

## API

| Метод | Тело | Ответ |
| --- | --- | --- |
| `POST /embed` | `{"inputs": ["…"] \| "…", "normalize": true}` | `[[f32 × 1024], …]` в порядке `inputs` |
| `POST /rerank` | `{"query": "…", "texts": ["…"], "raw_scores": false, "return_text": false}` | `[{"index": 2, "score": 0.93}, …]` по убыванию `score` |
| `GET /health` | — | `200`, когда обе модели загружены |
| `GET /info` | — | модели и ревизии, устройство, dtype, время загрузки, память MPS |

- Вектор BGE-M3 — CLS-токен последнего слоя, при `normalize: true` нормирован (L2 = 1), как у
  sentence-transformers и TEI для этой модели.
- `score` реранкера — сигмоида логита (0..1); `raw_scores: true` отдаёт логит.
- Ошибки в форме TEI: `{"error": "…", "error_type": "…"}`. Пустой `inputs`/`texts` — `400 Empty`,
  больше `ML_MAX_BATCH` текстов — `413 Validation`, неверное тело — `422 Validation`, сбой модели —
  `424 Backend`.
- Расхождение с TEI: TEI по умолчанию отказывает на текстах длиннее лимита модели (8192 токена), здесь
  всё обрезается до 512. Карточки и запросы короче, но бэкенду лучше не слать длинные описания.
- Тексты запросов в журнал не попадают, пишется только строка доступа (метод, путь, статус).
- Моделью владеет один поток (`embedder/batcher.py`), MPS — одна очередь. Одновременные `/embed` идут в
  модель одной пачкой (до `ML_MAX_BATCH` текстов), одновременные `/rerank` — одной пачкой пар (до
  `ML_RERANK_BATCH`); пачки векторов и реранка чередуются, когда ждут оба. Память MPS та же, что у одного
  запроса максимального размера (allocated 2.2 ГБ, driver 3.3 ГБ после нагрузки). Под 20 потоками
  поиска: 33,5 → 58–62 запр./с без кэша API.

```
curl -s 127.0.0.1:8089/embed -H 'Content-Type: application/json' \
  -d '{"inputs":["программа для чертежей"],"normalize":true}' | head -c 120
curl -s 127.0.0.1:8089/rerank -H 'Content-Type: application/json' \
  -d '{"query":"программа для чертежей","texts":["Kaspersky Internet Security","Autodesk AutoCAD LT"]}'
```

## Проверка и замеры

```
python3 ml/test_service.py       # 10 проверок запущенного сервиса, только stdlib (или python -m pytest ml/test_service.py)
python3 ml/bench.py              # задержки и память запущенного сервиса (--json — машиночитаемо)
ml/.venv/bin/python ml/bench.py --precision   # fp16 против fp32 в одном процессе
```

Замеры на Mac mini M4 (10-ядерный GPU), 24 ГБ, torch 2.15.0, transformers 5.24.1, fp16 на MPS.
Карточки — 64 синтетические карточки по 42–53 токена (название, лицензия, 2 предложения описания).
На машине параллельно шли сборки других треков, поэтому разброс в несколько миллисекунд — шум.

| Что | Результат |
| --- | --- |
| Загрузка обеих моделей + прогрев (в процессе) | 8.6 с: BGE-M3 3.2 с, реранкер 3.2 с, прогрев форм 2.2 с |
| От `run.sh start` до `/health = 200` (модели в кеше) | 11.5 с (с нуля, с созданием venv и pip из кеша — 50 с) |
| Память процесса | phys_footprint 4.4 ГБ (после 150 запросов разной формы не растёт; разовый пик 5.3 ГБ), из них MPS: веса 2.2 ГБ, всего у драйвера 3.2 ГБ; RSS 0.1–0.8 ГБ не показателен — память MPS в него не входит |
| `/embed`, 1 запрос | p50 18 мс, p95 19–26 мс |
| `/embed`, 64 карточки | p50 660–720 мс, p95 670–730 мс (≈ 90–100 карточек/с) |
| `/rerank`, запрос + 20 карточек | p50 243–260 мс, p95 244–265 мс |
| Размерность | 1024, норма 1.0 |
| Запасной режим `ML_DEVICE=cpu` (fp32) | загрузка 15 с; `/embed` x1 p50 49 мс, x64 p50 1.6 с; `/rerank` q+20 p50 640 мс; 10/10 проверок |

Качество fp16 против fp32 на MPS (`bench.py --precision`, 4 запроса × 64 карточки): косинус между
векторами fp16 и fp32 — минимум 0.99999; топ-10 ближайших карточек совпадает 10 из 10 для каждого
запроса; максимальная разница оценок реранкера 0.0009, порядок топ-5 одинаковый. Поэтому на MPS
по умолчанию fp16.

Скорость упирается в вычисления GPU (≈3 TFLOPS fp16 на базовом M4): `/rerank` растёт линейно от
суммарного числа токенов пар «запрос + текст», поэтому реранкеру лучше отдавать короткий текст
карточки (название + лицензия + первое предложение) и не больше 20–30 кандидатов.
