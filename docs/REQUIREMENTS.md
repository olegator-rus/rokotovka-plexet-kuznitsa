# Требования заказчика: где они в продукте

Короткая карта: требование, экран или метод, чем подтверждено. Каталог везде — фид магазина, 136 040 предложений.
Подробная таблица «требование, код, тест, доказательство» лежит в [REQUIREMENTS_MATRIX.md](REQUIREMENTS_MATRIX.md),
методика и оговорки к числам — в [EVALUATION.md](EVALUATION.md).

Разделы продукта: «Поиск» `/search` (витрина), «SearchOps» `/searchops` (бэк-офис: «Отчёт», «Запросы без ответа»,
«Запуски», «Очередь», «Память», «Изменения», «Политика ранжирования») и «Доказательства» `/proofs` («На данных
заказчика», «Стоимость», «Вклад компонентов», «Контроль улучшений», «Теоретические основы» и другие экраны оценки).

Сверх требований сделаны две вещи, которые заказчик назвал гипотезой:

- **ИИ-консультант.** Окно переписки на витрине, включено по умолчанию. Задаёт уточняющий вопрос, сравнивает редакции
  по базе знаний, подбирает лицензию под число мест и кладёт её в спецификацию. Режим подбора решил 52 диалога из 52,
  в трёх прогонах 156 из 156 (набор настройки). Прежний помощник подбора остался запасным режимом и открывается по
  адресу с `?consultant=0`.
- **Поиск по ТЗ.** Покупатель загружает DOCX, PDF или скан. Модель выделяет позиции с дословной цитатой требований,
  по каждой позиции идёт обычный поиск. На тестовом документе из 8 позиций во всех трёх форматах найдены одни и те же
  8 позиций, с ожидаемым ответом сходятся 6.

Независимая проверка всего поиска — отложенный набор: 83 трудных запроса, которых поиск не видел, один прогон после
заморозки. Целевая страница первым ответом в 66 запросах из 83, у текстового поиска в 37
([CLOSED_SET_RUN.md](CLOSED_SET_RUN.md)).

## Кому что достаётся

Вход выполняется по ролям. Решение по правке сервер принимает только от роли-владельца причины.

| Роль в продукте | Что получает | Где |
| --- | --- | --- |
| Гость, покупатель | Выдачу с объяснением, подсказки, ИИ-консультанта, поиск по ТЗ, спецификацию и запрос КП. Вошедший демо-покупатель видит пометку «Вы покупали» у купленных лицензий | «Поиск» |
| Администратор поиска | Причины «поиск не понял запрос», «товар стоит низко», «запрос не о товаре»; правки словаря, проверенные прогоном; версии правил и откат | «Очередь», «Изменения» |
| Категорийный и лицензионный менеджер | Причины «товара нет в каталоге», «нет факта в базе знаний» | «Очередь» |
| Каталог | Причину «найдено, но только по запросу»: позиции, которым нужна цена и наличие | «Очередь» |
| Руководитель e-com | Всё перечисленное, шум и неразобранное, режим агента «только чтение», стоимость | SearchOps, «Доказательства» |

Первый экран SearchOps, «Отчёт», написан для маркетолога: спрос без предложения, товар есть, но не найден, слова
покупателей вне каталога, сервисные вопросы. Экран показывает сохранённые проверки сразу и обновляет их в фоне.

## Нефункциональные требования

| Требование | Как закрыто | Подтверждение |
| --- | --- | --- |
| Время ответа | Языковая модель только на маршруте D, разборы кэшируются; реранкер только на маршрутах C и D | Эталоны, полный продукт: 72 мс по медиане, 127 мс p95 (тёплый прогон, время сервера без сети). Отложенный набор без кэша: 144 мс по медиане, 1 994 мс p95 на запросах с разбором моделью |
| Работа без внешней модели | `LLM_MODE=off` или режим «без моделей», без перезапуска. Сверх дневного бюджета — тоже правила и кэш | На журнале поиска по фиду Hit@1 по семейству без модели тот же, 85,9 %. Тесты отказов `TestFailoverAllModelsDown`, `TestFailoverRerankerDown` |
| Защита от перегрузки и перерасхода | Лимит 600 запросов в минуту с адреса, срок обработки запроса 25 с, дневной бюджет модели 1 000 ₽, квота 20 ₽ в сутки на адрес, пределы запуска агента | Значения по умолчанию в `backend/.env.example`; [COSTS.md](COSTS.md) |
| Объяснимость | Трассировка каждого запроса: шаги, время, вызывалась ли модель; у карточки подписаны тип совпадения и причина | Переключатель «Трассировка» на витрине, `GET /api/traces/{request_id}` |
| Стоимость | Учёт каждого вызова модели, формула стоимости запроса | 0,57 ₽ за запрос при 15 000 запросов в месяц, из них модель 0,0027 ₽ — [COSTS.md](COSTS.md) |
| Интеграция | Независимый HTTP API, не привязан к CMS; каталог подключается файлом соответствия полей | [openapi.yaml](openapi.yaml), [INTEGRATION.md](INTEGRATION.md), [PILOT.md](PILOT.md) |
| Безопасность | Вход по ролям, права проверяет сервер, изменяющие запросы только с адреса стенда, ответ модели сверяется со справочником | Модель угроз в [ARCHITECTURE.md](ARCHITECTURE.md#модель-угроз); сквозной тест `e2e/tests/roles.spec.ts` |
| Персональные данные перед внешней моделью | Маскируются телефон, почта, ИНН, КПП, ОГРН, номер карты, СНИЛС, паспорт; имена и адреса в запросе не распознаются | [DATA_FLOW.md](DATA_FLOW.md) |
| Рекомендательные технологии | Строка в подвале и страница `/rules`: какие данные используются и как формируется блок дополнений | Текст страницы — заготовка для юриста заказчика, юридической оценки не было |

## Что данными заказчика не закрывается

- Цен конкурентов в данных нет. «Выгоднее» означает скидку фида, акцию магазина или сравнение редакций одной линейки.
- Маржи, заказов, кликов и логов поиска в данных нет. Слагаемые маржи и популярности в итоговом ранжировании порядок
  не меняют, агент работает на тестовом трафике.
- Полный перечень ограничений приведён в корневом [README](../README.md), раздел «Ограничения и допущения».
