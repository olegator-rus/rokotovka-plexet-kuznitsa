# Договор об интеграции

Как PLEXeT подключается к магазину, не заменяя корзину, карточку товара и оформление. Методы — [openapi.yaml](openapi.yaml),
форматы данных — `data/README.md`. Статус каждой строки — что есть в
коде сейчас; «нет» значит «нет», а не «почти готово». Интеграции с магазином мы не делали: всё ниже проверено на
mock-данных.

## Схема

```
           МАГАЗИН (остаётся у магазина: витрина, карточка, корзина, счёт, кабинет, Mindbox)
   каталог, цены, наличие,        │                       ▲  выдача, подсказки, трасса,
   связи и правила, события        ▼                       │  заявки и КП, сигналы спроса
           ┌──────────────────────────────────────────────────────────┐
           │ PLEXeT API: /search, /suggest, /events, /quotes            │
           │ OpenSearch, сервис моделей, PostgreSQL — свой сервер       │
           │ Бэк-офис SearchOps: агент, очередь, версии правил, откат   │
           └──────────────────────────────────────────────────────────┘
```

## Что читаем из магазина

| Данные | Зачем | Формат сейчас | Статус |
| --- | --- | --- | --- |
| Каталог: позиции, семейства, варианты лицензий (тип покупки, срок, метрика, количество, тип организации), характеристики, категории, вендоры | Индекс поиска, лицензионные фасеты, вариант по запросу | `catalog.json` и справочники | Есть адаптер только для mock-JSON; адаптер под выгрузку магазина — первая неделя пилота |
| Цены | Цена «от» по подходящим вариантам, сумма КП | Поле позиции `price_rub`, `price_on_request` | Есть (каталожные цены); договорных цен нет и не нужны поиску |
| Наличие и срок поставки | Фасет и подпись в выдаче | — | **Нет**: поля в данных нет, в пилот (главная жалоба покупателей — по ресерчу) |
| Связи и правила: аналоги, продления, обязательные компаньоны, совместимость | Аналоги, честное «нет» с заменой, строка обязательного | `relations.json`, `license_rules.json`, `compatibility_rules.json` | Есть |
| Реестр российского ПО, сертификаты | Статус в трёх состояниях | Атрибут варианта | Делается в на нескольких семействах mock-каталога |
| События: показ, клик, корзина, заказ, запрос цены — с `request_id` поиска | Аналитика неудач, вход агента, оценка пилота | `POST /api/events` | Есть приёмник; витрина магазина их пока не шлёт |
| Журнал поиска за 30–90 дней | Наборы tune/test, первые запуски агента | `events.jsonl` или выгрузка | Есть импорт mock-логов |

Импорт строит новый индекс рядом и атомарно переключает алиас: поиск во время импорта не прерывается
(`POST /api/catalog/import` перечитывает настроенный источник).

## Что отдаём

| Метод | Что | Кто вызывает | Статус |
| --- | --- | --- | --- |
| `POST /api/search` | Выдача семействами с выбранным вариантом, чипы понятого запроса, «нет в каталоге» и аналоги, трасса | Сервер витрины (или фронт магазина через свой прокси) | Есть |
| `GET /api/suggest`, `/api/suggest/recommendations` | Подсказки и товары на ввод, без LLM и без векторов | Витрина | Есть |
| `POST /api/events` | Приём событий витрины | Витрина | Есть |
| `POST /api/quotes` | Заявка и КП: позиции, количество, исходный запрос и параметры (тип покупки, срок, тип организации —) | Витрина; дальше — CRM или спецификатор магазина | Есть приём; передача в CRM/спецификатор — нет, формат согласовать |
| Сигналы спроса | Чего нет в каталоге, что ищут и не находят — задачи владельцам причин | Бэк-офис SearchOps (категорийный менеджер, каталог) | Есть в бэк-офисе; выгрузки во внешние системы нет |

## Как подключаемся без замены корзины и карточки

1. **Теневой режим.** Сервер витрины параллельно с текущим поиском вызывает `POST /api/search` (с таймаутом, например
   300 мс) и пишет ответ в журнал; покупатель видит старую выдачу. Ничего в интерфейсе магазина не меняется.
2. **Выдача.** Витрина рисует результаты своими карточками по `product_id` из ответа; «В корзину» ведёт в корзину
   магазина. Трассу можно не показывать.
3. **Подсказки** — тот же принцип: `GET /api/suggest` вместо текущего источника подсказок.
4. **События** — `POST /api/events` с `request_id` поиска: без них не работают аналитика, агент и оценка пилота.
5. **Отказ.** Если API не ответил в срок, витрина показывает свой поиск: PLEXeT не становится точкой отказа магазина.
   Внутри PLEXeT отказ моделей тоже не роняет поиск (тесты отказов, режим «без моделей» — [DATA_FLOW.md](DATA_FLOW.md)).

Бэк-офис (SearchOps, доказательства) работает отдельно от витрины, закрыт входом сотрудника или токеном
`BACKOFFICE_TOKEN`; витрине вход не нужен.

## Что нужно от магазина

Выгрузка каталога и правил, журнал поиска, события с `request_id`, сервер (или облако) под API, OpenSearch и сервис
моделей, ответственные за причины неудач (администратор поиска, категорийный менеджер, каталог). Что из этого и когда —
[PILOT.md](PILOT.md).
