# Движение данных: что уходит во внешнюю модель

Документ отвечает на один вопрос: какие данные покидают сервер и уходят во внешнюю языковую модель. Источник — код
(`backend/services/intent.go`, `consultant_reply.go`, `tz_extract.go`, `agent_*.go`, `eval_judge.go`,
`backend/externalApi/llm/`) и журнал вызовов модели `llm_usage`. Юридической оценки по закону о персональных данных не
было. В фиде персональных данных нет. Какие поля клиента передавать в пилоте, решает заказчик.

## Схема

```
Покупатель ──запрос──▶ PLEXeT API ──────────────▶ OpenSearch (свой сервер): индекс каталога
                         │  │
                         │  └──текст запроса, карточки──▶ сервис моделей (свой сервер): BGE-M3, реранкер
                         │
                         ├──только маршрут D и только при промахе кэша──▶ Yandex AI Studio (внешняя модель)
                         │     нормализованный текст запроса, сегмент, отбор справочника категорий и вендоров
                         ├──ход ИИ-консультанта──▶ Yandex AI Studio
                         │     реплика, последние реплики разговора, лист фактов из каталога и базы знаний
                         └──поиск по ТЗ──▶ Yandex AI Studio
                               текст документа после маскирования

Агент SearchOps (фон или кнопка «Разобрать») ──группы неудачных поисков, карточки, алиасы, прогоны──▶ Yandex AI Studio
Оценка (не на витрине) ──запрос и карточка, вслепую──▶ модель-судья (qwen3.6-35b-a3b, Yandex AI Studio)
```

## Что уходит и что нет

| Вызов | Когда | Что уходит | Что не уходит |
| --- | --- | --- | --- |
| Разбор намерения | Маршрут D и только при промахе кэша разборов. По журналу витрины на фиде модель разбирает 13,5 % поисков, 83,5 % разборов берутся из кэша. Не вызывается в режиме без модели и сверх дневного бюджета | Нормализованный текст запроса — строкой JSON, как данные; сегмент покупателя (`smb`, `enterprise` и т. п.); отбор справочника: до 15 категорий и 20 вендоров, совпавших со словами запроса | Идентификатор клиента, номер сессии, адрес, история покупок, цены, маржа. Телефон, почта, ИНН и другие номера из текста запроса заменены метками |
| ИИ-консультант | Каждый ход подбора: до двух вызовов. Сервисные вопросы и изменения спецификации обходятся без модели | Реплика покупателя (до 500 знаков), до восьми последних реплик разговора, лист фактов: позиции каталога с ценами и факты базы знаний | Идентификатор клиента и номер сессии. Номера из реплик заменены метками |
| Поиск по ТЗ | Загрузка документа. Вызов модели идёт на каждую позицию, и в каждый уходит текст документа | Текст документа после маскирования. Кроме номеров, маскируются ФИО контактных лиц (метка `[фио]`) | Сам файл. Под хешем на неделю сохраняются только позиции с цитатами, без файла и полного текста |
| Агент SearchOps | По расписанию, по всплеску неудачных поисков, при смене каталога или по кнопке «Разобрать» | Тексты неудачных запросов с частотами (без сессий), карточки каталога (название, вендор, категория, описание, условия лицензии, цена), действующие алиасы, результаты прогонов | Идентификаторы клиентов и сессий, история конкретного клиента |
| Модель-судья | Только при оценке (`go run . judge`), на работу витрины не влияет | Текст запроса из набора и карточка товара | Конфигурация поиска и место товара в выдаче (оценка вслепую) |
| Эмбеддер и реранкер | Вектор запроса — каждый гибридный поиск; реранкер — маршруты C и D | Текст запроса и тексты карточек | Наружу не уходят: свой сервис на своём сервере (`EMBEDDER_URL`, `RERANKER_URL`) |

Сканы ТЗ на стенде распознаёт tesseract на сервере, наружу страницы не уходят. Облачное распознавание Yandex Vision
OCR поддержано настройкой `OCR_URL`. Если его включить, изображения страниц будут уходить в этот сервис.

Проверено тестом `TestInjectionAndNoClientIDs`: запрос уходит модели как данные, идентификаторы клиента и сессии в
тело вызова не попадают, значения, которых нет в справочнике, отбрасываются.

## Маскирование персональных данных

Перед любым вызовом внешней модели клиент модели (`backend/externalApi/llm/pii.go`) заменяет в тексте сообщений и в
аргументах вызовов инструментов телефоны, e-mail, ИНН, КПП, ОГРН и ОГРНИП, номера карт, СНИЛС и паспорт на метки
`[телефон]`, `[email]`, `[инн]`, `[кпп]`, `[огрн]`, `[карта]`, `[снилс]`, `[паспорт]`. Через этот клиент идут все
вызовы: разбор намерения, консультант, разбор ТЗ, агент и судья. Разбор намерения маскирует запрос ещё до ключа кэша,
поэтому в кэш попадает текст с метками, а в трассировке у шага разбора стоит число замаскированных фрагментов.

Тесты: `TestChatMasksPIIInRequestBody` (тело запроса к подменному серверу), `TestSearchRouteDMasksPII` (весь путь
поиска до маршрута D), `TestIntentMasksPIIBeforeModelAndCache` (кэш), `TestMaskPIINoFalsePositivesOnRepoData` (ложные
срабатывания на данных репозитория), `TestTZMaskNames` (ФИО в тексте ТЗ).

Чего маскирование не умеет. Оно работает по формату и контрольным суммам. Имя и адрес в поисковом запросе и в реплике
консультанту оно не распознаёт; ФИО маскируются только в тексте ТЗ. Номер без узнаваемого формата пройдёт как есть.
Число, которое случайно совпало с форматом, будет заменено меткой. Строка поискового запроса в журнал сервера не
пишется.

## Провайдер

Yandex AI Studio (Yandex Cloud), API совместим с OpenAI. Языковая модель одна, Alice AI LLM Flash: разбор намерения,
консультант, разбор ТЗ и агент. Модель-судья qwen3.6-35b-a3b используется только при оценке. Адрес и модель задаются
переменными `LLM_BASE_URL` и `LLM_MODEL`, резервная модель разбора — `LLM_FALLBACK_MODEL` (по умолчанию не задана).
Ключ читается только из окружения сервера и во фронтенд не попадает.

Вариант в контуре заказчика — модель с открытыми весами за сервером, совместимым с OpenAI: меняется только адрес. Мы
такой вариант не разворачивали и качество на нём не мерили.

## Режим без модели

| Настройка | Что выключает | Как переключить | Что остаётся |
| --- | --- | --- | --- |
| `LLM_MODE=off` | Внешнюю модель | Без перезапуска: `POST /api/admin/llm-mode {"mode":"off"}` | Маршрут D на правилах и кэше разборов; агент не запускается |
| Режим «без векторов» | Эмбеддер и реранкер | `POST /api/admin/vectors-mode {"mode":"off"}` | Текстовый поиск, словарь, атрибуты, порог, итоговое ранжирование |
| «Без моделей» | И языковую модель, и векторы | `POST /api/admin/offline-mode {"mode":"on"}` | Поиск по тексту, правилам и кэшу |

Служебные методы доступны только сотруднику и только при `ADMIN_ENABLED`.

Что это стоит по качеству, измерено на журнале поиска по фиду (180 запросов, [EVALUATION.md](EVALUATION.md)): без
языковой модели Hit@1 по семейству тот же, 85,9 %; без векторной ветки он падает до 74,6 %. Отказ сервисов проверен
тестами `TestFailoverAllModelsDown` и `TestFailoverRerankerDown`: эмбеддер и реранкер недоступны, модель отвечает
дольше срока — поиск отвечает, пропущенные шаги записаны в трассировке с причиной.
