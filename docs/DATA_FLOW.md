# Движение данных: что уходит во внешнюю модель

Ответ на вопрос «какие данные уходят во внешнюю модель» одной страницей. Источник — код (`backend/services/intent.go`,
`agent_*.go`, `eval_judge.go`) и журнал вызовов `llm_usage`. Юридической оценки (152-ФЗ) не было: в mock-данных
персональных данных нет, решение о полях клиента в пилоте принимает заказчик.

## Схема

```
Покупатель ──запрос──▶ PLEXeT API ──────────────▶ OpenSearch (свой сервер): индекс каталога
                         │  │
                         │  └──текст запроса, карточки──▶ Сервис моделей (свой сервер): BGE-M3, реранкер
                         │
                         └──только маршрут D и только при промахе кэша──▶ Yandex AI Studio (внешняя модель)
                              нормализованный текст запроса + сегмент («smb») + справочники категорий/вендоров

Агент SearchOps (фон: ночь, всплеск, смена каталога; «Разобрать») ──агрегаты неудачных поисков, карточки, алиасы, прогоны──▶ Yandex AI Studio
Оценка (офлайн, разработка) ──запрос + карточка, вслепую──▶ LLM-судья (Qwen3.6 35B, Yandex AI Studio)
```

## Что уходит и что нет

| Вызов | Когда | Что уходит | Что не уходит |
| --- | --- | --- | --- |
| Разбор намерения | Маршрут D (29,7 % запросов test), только при промахе кэша разборов; не в режиме «без LLM» и не сверх дневного бюджета | Нормализованный текст запроса — JSON-строкой внутри тега `<query>`, как данные; сегмент покупателя (`smb`, `enterprise`, …); справочники категорий и вендоров в инструкции | id клиента, номер сессии, адрес, история покупок, ИНН, договорные цены, маржа; телефон, почта, ИНН и другие номера из текста запроса — заменены метками |
| Агент SearchOps | Сам по триггерам — ночь по расписанию, всплеск неудачных поисков, смена каталога (`AGENT_SCHEDULE`, по умолчанию выключено; на стенде включается) — или «Разобрать» на одном запросе | Тексты неудачных запросов с частотами (агрегаты журнала, без сессий), карточки каталога (название, вендор, категория, описание, условия лицензии, каталожная цена), действующие алиасы, результаты прогонов | id клиентов и сессий, история конкретного клиента, договорные цены, маржа (диагноз по марже удалён в контуре доводки) |
| LLM-судья | Только офлайн-оценка разработчиком (`go run . judge`) | Текст запроса из размеченного набора и карточка товара | Конфигурация поиска и позиция товара (вслепую) |
| Эмбеддер и реранкер | Каждый поиск B2–B3 (кроме режима «без векторов») | Текст запроса и тексты карточек | Наружу не уходят: свой сервис на своём сервере (`EMBEDDER_URL`, `RERANKER_URL`) |

Проверено тестом `TestInjectionAndNoClientIDs`: запрос уходит модели данными, id клиента и сессии в тело вызова не
попадают, подложенные моделью значения отбрасываются сверкой со справочниками.

**Маскирование персональных данных.** Перед любым вызовом внешней модели клиент (`backend/externalApi/llm/pii.go`,
`Client.Chat`) заменяет в тексте каждого сообщения и в аргументах вызовов инструментов телефоны (российские и
международные), e-mail, ИНН, КПП, ОГРН/ОГРНИП, номера карт, СНИЛС и паспорт на метки `[телефон]`, `[email]`, `[инн]`,
`[кпп]`, `[огрн]`, `[карта]`, `[снилс]`, `[паспорт]`. Через этот клиент идут все вызовы: разбор намерения, агент,
судья и классификатор наборов. Разбор намерения маскирует запрос ещё раньше, поэтому в кэш разборов (ключ и
сохранённый текст) попадает текст с метками, а в трассе поиска у шага «Намерение» стоит «замаскировано: N».
Проверено тестами: `TestChatMasksPIIInRequestBody` (тело запроса к подменному серверу без телефона, почты, ИНН и
карты), `TestSearchRouteDMasksPII` (весь путь поиска до маршрута D), `TestIntentMasksPIIBeforeModelAndCache` (кэш),
`TestMaskPIINoFalsePositivesOnRepoData` (0 ложных срабатываний на каталоге, наборах запросов, событиях и промптах).

**Чего нет и что честно сказать.** Маскирование работает по формату и контрольным суммам. Имя и фамилию оно не
распознаёт, адрес тоже. Номер без формата и без контрольной суммы (например, 10 цифр после слова «телефон», но не
похожие на телефон) пройдёт как есть. Число, которое случайно совпало с форматом, будет заменено меткой; на mock-данных
таких нет. Шум (SQL, разметка, одни знаки) на маршрут D не идёт. Юридической оценки (152-ФЗ) не было.

## Провайдер

Yandex AI Studio (Yandex Cloud, российский провайдер), OpenAI-совместимый API. Модели: Alice AI LLM Flash — разбор и
агент; Qwen3.6 35B — резерв разбора и судья. Адрес и модель — переменные `LLM_BASE_URL`, `LLM_MODEL`; ключ — только
из окружения сервера, во фронтенд не попадает. Вариант в контуре заказчика — модель с открытыми весами за
OpenAI-совместимым сервером: код не меняется, только адрес; мы его не разворачивали и качество на нём не мерили.

## Режим без модели

| Настройка | Что выключает | Как переключить | Что остаётся |
| --- | --- | --- | --- |
| `LLM_MODE=off` | Внешнюю модель | Без перезапуска: `POST /api/admin/llm-mode {"mode":"off"}` | Маршрут D на правилах и кэше разборов; агент не запускается (409) |
| Режим «без векторов» | Эмбеддер и реранкер | `POST /api/admin/vectors-mode {"mode":"off"}` | Текстовый поиск, словари, атрибуты, порог, бизнес-слой |
| **«Без моделей» — одна настройка** | И LLM, и векторы | `POST /api/admin/offline-mode {"mode":"on"}`, кнопка «Без моделей» на экране «Доказательства → Вклад компонентов» (сотрудник) | Поиск по тексту, правилам и кэшу; плашка режима в `GET /api/meta → vectors.banner` |

Служебные методы — только со входом сотрудника и при `ADMIN_ENABLED` (в production по умолчанию выключен).

Что даёт режим (строка B3-M таблицы вклада, test): поиск отвечает на все 148
запросов без ошибок, NDCG@10 0,815 против 0,892 у полного пути, пустых 11,5 % против 7,4 %, точные на 1-м месте
93,5 % против 100 %, P95 5,9 мс. Тесты отказов (`backend/services/eval_contribution_failover_test.go`): лежат
эмбеддер и реранкер, модель отвечает дольше срока — поиск отвечает, шаги пропущены с причиной в трассе.
